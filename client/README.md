# To-Do List – Frontend

A single-page to-do app built with React and Vite. It talks to the Express/MongoDB API in the `server/` folder.

## Tech stack

- React 19 + Vite 7
- Tailwind CSS v4
- **shadcn/ui** for the UI component library and base styling (see "Generated code: shadcn/ui" below)
- lucide-react icons
- react-hook-form + zod for form validation
- axios for API calls, sonner for toast notifications

## Prerequisites

- Node.js 20 or newer (recommended) and npm
- The backend running locally (see `../server/README.md`)

## Setup

1. Install dependencies. In the monorepo, run this **once from the repository root** (it installs both apps):

   ```bash
   npm install
   ```

2. Create your environment file:

   ```bash
   cp .env.example .env
   ```

   On Windows (cmd): `copy .env.example .env`

3. Check the API URL in `.env`:

   ```
   VITE_API_URL=http://localhost:5000/api
   ```

   It must include `/api`, have no trailing slash, and point at wherever the backend is running. Vite reads this value only at startup, so **restart the dev server after changing it**.

## Running the app

Start the backend first, then:

From the repository root, `npm run dev` starts both apps together. To run only the frontend:

```bash
npm run dev -w client
```

The app is served at <http://localhost:5173>.

| Command           | What it does                                    |
| ----------------- | ----------------------------------------------- |
| `npm run dev`     | Starts the Vite dev server with hot reload      |
| `npm run build`   | Creates a production build in `dist/`           |
| `npm run preview` | Serves the production build locally to test it  |

## Features

- View all tasks, with **All / Pending / Completed** tabs that show a live count for each
- Add a task (title required, description up to 500 characters)
- Edit a task's title and description
- Mark a task done, or back to pending, with one click
- Delete a task, after a confirmation dialog
- Toast messages for success and failure, plus loading and empty-state messages

## Project structure

```
src/
  App.jsx              page layout; loads todos, holds filter state and tab counts
  components/          TaskList, TaskCard, TaskFormModal, DeleteTaskDialog
    ui/                shadcn/ui components, generated by the shadcn CLI (not hand-written)
  services/
    api.js             axios instance (reads VITE_API_URL)
    todoService.js     API functions used by the components
  layouts/             AppShell wrapper
  index.css            global styles: Tailwind setup + shadcn theme variables (generated by shadcn)
  lib/                 utilities (utils.js is from shadcn)
```

## Generated code: shadcn/ui

This project uses [shadcn/ui](https://ui.shadcn.com). The following were **generated by the shadcn CLI** rather than written by hand:

- `components.json`: the shadcn configuration (style `base-sera`, base colour `zinc`, lucide icons, `@/` path aliases).
- `src/components/ui/*`: the shadcn components (button, card, dialog, input, tabs, textarea, sonner toaster).
- `src/index.css`: the Tailwind imports, `shadcn/tailwind.css`, and the theme variables (colours, radius, dark mode) produced by shadcn's initialisation. A few small project-level rules (fonts, full-height `html`/`body`/`#root`) sit alongside them.
- `src/lib/utils.js`: shadcn's `cn()` class-name helper.

The application code is everything else: `App.jsx`, `components/TaskList.jsx`, `TaskCard.jsx`, `TaskFormModal.jsx`, `DeleteTaskDialog.jsx`, `layouts/AppShell.jsx`, and `services/*`. These compose the shadcn components into the to-do app and handle the API calls.

To add or regenerate a component, use the CLI, for example: `npx shadcn@latest add dialog`.

## Assumptions

- The backend is reachable at the URL in `VITE_API_URL`.
- Tasks have the shape the API returns: `_id`, `title`, `description`, `done`, `createdAt`.
- `PATCH /todos/:id/done` **toggles** a task between done and pending. The button label ("Mark done" / "Mark pending") depends on this.

## Limitations

- After every add, edit, toggle or delete, the whole list is reloaded from the server. This is simple, but it is not optimistic and there is no pagination, so very large lists will feel slower.
- If the first load fails (for example the server is down), the error is only logged to the console and the user sees an empty list rather than an error message.
- The title has no maximum length on the form (only the description is capped at 500 characters).
- Filtering by tab happens in the browser, on the full list.
